# 协作流程

## 一、十天排期

日期按 11 月 16 日开始、周末不计推算，以老师通知为准。

| 天 | 日期 | 目标 | 当天结束时应该有 |
|---|---|---|---|
| 1 | 11/16 周一 | 定方向 | 分组表已交；向老师确认需求卡的不确定项；仓库建好，全员能克隆、能推送；全员读完需求卡和需求清单 |
| 2 | 11/17 周二 | 搭骨架 | 组长合入骨架（数据类、建表、接口空壳、主窗口、登录）；其他人装好环境、跑通骨架，把自己负责的需求验收条件再细化一遍 |
| 3 | 11/18 周三 | 打通主干 | 首批任务卡开工；D 与 A 打通"入场 → 出场 → 记录可查" |
| 4 | 11/19 周四 | 基础功能 | 首批任务卡全部合入；第二批开工 |
| 5 | 11/20 周五 | 基础验收 | 基础功能 REQ-001 至 011 全部完成；主分支打标签 `v0.1`；组内互相演示一遍 |
| 6 | 11/23 周一 | 进阶功能 | 计费接入出场流程；统计页面出图 |
| 7 | 11/24 周二 | 进阶功能 | 进阶功能 REQ-012 至 023 完成；打标签 `v0.2` |
| 8 | 11/25 周三 | 变更演练与拓展 | 完成一次需求变更演练（见第六节）；拓展功能开工 |
| 9 | 11/26 周四 | 收尾 | 停止加新功能；修问题；准备演示数据；实训报告成稿 |
| 10 | 11/27 周五 | 答辩 | 每人能独立讲清自己的模块；打标签 `v1.0` |

排期的底线：第 5 天基础功能必须完成。进度落后时先砍拓展，再砍进阶，不压缩测试和报告。

## 二、每天的节奏

- **开工前 10 分钟**：每人说三句话：昨天完成了什么、今天做哪张任务卡、有没有被卡住。
- **开工第一件事**：拉取主分支最新代码，再从它建自己的分支。
- **收工前**：推送分支；在 `docs/实训日志.md` 写当天日志；组长确认主分支能启动、测试通过。

## 三、Git 最少要会的操作

第一天全员练一遍。

```bash
# 一次性：克隆仓库
git clone <仓库地址>
cd parking-system

# 每个任务：从最新的主分支建分支
git switch main
git pull
git switch -c feat/REQ-003-resident

# 写代码过程中：查看改动、提交
git status                         # 看改了哪些文件
git diff                           # 看具体改了什么
git add app/repository/resident_repo.py tests/test_repository_resident.py
git commit -m "feat(resident): 住户新增与按姓名查询 (#4)"

# 推送并在 GitHub 网页上发起合并请求
git push -u origin feat/REQ-003-resident

# 主分支有更新时，同步到自己的分支
git switch main && git pull
git switch feat/REQ-003-resident
git merge main
```

## 四、分支与提交规则

- 主分支 `main` 只通过合并请求更新，任何人不直接向它推送。建议在 GitHub 仓库设置里开启主分支保护。
- 分支名：`feat/REQ-编号-简短英文`，修问题用 `fix/简短英文`。
- 一个分支只做一张任务卡。任务卡较大时可以分多次提交，但每次提交都应该是一个完整的小步骤。
- 提交信息写"行为发生了什么变化"，并带上 Issue 编号。
- **Issue 编号不等于 REQ 编号。** 仓库里 #1 是第 1 天日志的合并请求，需求 Issue 从 #2 开始，所以 **REQ-N 对应 Issue #(N+1)**，例如 REQ-003 住户增删改查是 #4。以 Issue 页面显示的编号为准。

| 不好 | 好 |
|---|---|
| `更新` | `feat(vehicle): 登记车辆时拒绝重复车牌 (#5)` |
| `修bug` | `fix(billing): 恰好 30 分钟应免费 (#13)` |
| `最终版` | `test(stats): 补充跨月收入统计用例 (#18)` |

- 提交前用 `git status` 确认没有带上 `data/`、`__pycache__/`、`.venv/` 和无关文件。

## 五、合并请求的检查

**提交人自查**（合并请求模板中有勾选项）

- 只改了任务卡允许的文件
- `pytest` 全部通过，结果贴在合并请求里
- 任务卡的每条验收条件都有对应的测试或截图
- 能不看代码讲清核心逻辑

**组长审查**

1. 改动的文件是否在任务卡允许范围内。
2. 测试是否断言了验收条件里的具体数值，而不只是"运行不报错"。
3. 有没有违反分层规则，例如界面里写了 SQL 或计费公式。
4. 请提交人口头讲一遍核心逻辑。讲不清就先不合并。

组长自己的合并请求由 D 或 E 审查。

**出现冲突时**：先在组内群里说明，由相关的两个人一起看。冲突的本质是两个人对同一处有不同的想法，先对齐想法再改代码，不要让 AI 助手直接选一边覆盖。

## 六、第 8 天的需求变更演练

目的：检验架构能不能承受变化，并为答辩准备一个有说服力的例子。

做法：由组长提出一条新需求，例如"新增一种车辆类型：业主亲属车，每次前 4 小时免费，之后每小时 2 元，每 24 小时封顶 20 元"。然后记录：

1. 改了几个文件、分别是哪些。
2. 有没有不得不修改的旧代码，为什么。
3. 原有测试是否全部仍然通过。
4. 从提出到合并用了多长时间。

把结果写进实训报告的"系统测试"或"实训总结"部分。改动集中在少数文件、旧测试全部通过，就说明分层和多态的设计起了作用；如果改动扩散到很多地方，如实记录原因和改进想法，同样是有价值的总结。

## 七、使用 AI 助手的规则

1. 开工时把任务卡完整交给助手，不要只说一句"帮我写住户管理"。
2. 仓库根目录的 `AGENTS.md` 是给助手的项目规则。第一天各自验证一次：问助手"这个项目有哪些硬规则"，能答出来说明已生效。
3. 每次只让助手推进一小步，做完先运行测试、看改动，再继续。
4. 助手说"完成了"不算完成。以 `pytest` 结果和验收条件为准。
5. 助手想修改任务卡范围以外的文件时，停下来找对应负责人，不要直接同意。
6. 每完成一张任务卡，自己做一次检验：改一个条件（例如把免费时长从 30 分钟改成 15 分钟），不靠助手说出要改哪里。答辩查的就是这个能力。
7. 遇到同一种错误出现第二次，考虑把它变成一条测试或写进 `AGENTS.md`，而不是每次口头提醒。
