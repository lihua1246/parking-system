# 决策记录

只记录有取舍的重要选择。普通修改用提交信息说明即可。
每条记录回答：为什么要选、选了什么、代价是什么、什么情况下重新考虑。

状态取值：暂定（等确认）/ 已采纳 / 已替换。

## ADR-001：界面采用 PySide6 桌面程序

**状态**：暂定，等老师确认界面要求（需求卡 Q1）

**背景**：任务书没有规定界面形式。需要在命令行、Tkinter、PySide6、网页之间选择。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 命令行 | 最省事 | 表格、图表展示困难，答辩演示效果差 |
| Tkinter | 标准库自带，不用安装 | 表格和布局能力弱，界面简陋 |
| PySide6 | 表格、对话框、图表嵌入都成熟，外观接近正式软件 | 需要安装，概念比 Tkinter 多 |
| 网页（Flask） | 界面自由度高 | 要额外学 HTML 和前后端交互，两周内风险大 |

**决定**：PySide6。

**原因**：系统以表格和表单为主，PySide6 的表格控件直接可用；全员使用自己的电脑，安装不是问题；有 AI 助手辅助，学习成本可接受。

**代价**：新增一个较大的依赖；组员需要理解信号与槽的基本用法。

**重新评估的条件**：老师明确要求网页或命令行；或第 3 天 MVP 时界面进度明显拖后。由于界面与业务规则分层，更换界面只影响 `app/ui/`。

## ADR-002：数据存储采用 SQLite

**状态**：暂定，等老师确认数据库要求（需求卡 Q2）

**背景**：任务书要求掌握数据库设计，但未指定数据库。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 文本或 JSON 文件 | 最简单 | 查询、唯一约束都要自己写，体现不出数据库设计 |
| SQLite | 标准库自带，数据库就是一个文件，换电脑演示不用配置 | 不适合多人同时写入 |
| MySQL | 更接近企业环境 | 每人都要安装和配置服务，答辩现场连接失败的风险高 |

**决定**：SQLite。

**原因**：系统单机使用，没有并发需求；五个人的环境零配置即可一致；测试可以用内存库，速度快且互不影响。

**代价**：没有练到数据库服务的安装与账号管理。

**重新评估的条件**：老师要求使用 MySQL。届时只需修改 `app/repository/db.py` 的连接方式和少量 SQL 方言差异。

## ADR-003：业务规则与界面、数据库分离

**状态**：已采纳

**背景**：计费和统计是最容易出错的部分。如果公式写在按钮的点击事件里，每次验证都要启动程序、手工录入、肉眼核对，五个人各自用 AI 助手开发时尤其难以发现错误。

**决定**：计费、统计、预警、校验全部放在 `app/services/`，写成不依赖界面和数据库的类或函数；当前时间由调用方传入。

**原因**：这样可以用固定的输入直接断言输出，例如"停 31 分钟应收 3 元"；负责人和 AI 助手都有明确的对错标准；界面和数据库更换时规则不用重写。

**代价**：文件数量变多；一个功能要分别在三层各写一部分，初学时会觉得绕。

**重新评估的条件**：无。这是本项目的基本结构。

## ADR-004：出入记录只增不删，并保存入场时的车辆信息副本

**状态**：已采纳

**背景**：出入记录是收费和统计的依据。如果允许删除或随意修改，统计结果无法解释；如果记录只保存车辆编号，车辆资料后来被修改或删除，历史记录就会失真。

**候选方案**

1. 普通增删改查，记录通过外键关联车辆表。
2. 记录只允许新增和补全出场信息，并在记录中保存入场时的车牌和车辆类型。
3. 完整的事件溯源：所有数据都由事件回放得到。

**决定**：方案 2，且只用于出入记录这一张表。住户、车辆、车位仍是普通增删改查。

**原因**：出入记录是"发生过的事实"，需要长期可信；其他资料是"当前状态"，普通增删改查足够。方案 3 对两周的项目来说成本过高，收益不明显。

**代价**：车牌和类型在两张表中各存一份；录错的记录不能删除，只能通过备注说明。

**重新评估的条件**：如果确实需要更正错误记录，增加"更正记录"功能（新增一条说明，保留原记录），而不是开放删除。

## ADR-005：金额用整数，按 24 小时周期封顶

**状态**：已采纳

**背景**：停车费需要精确计算并与手算结果比对。"每日封顶"有两种理解：按自然日（0 点到 24 点），或按入场后每满 24 小时。

**决定**：金额用整数（单位：元）。封顶按入场后每 24 小时为一个周期计算。

**原因**：浮点数做金额运算会出现 0.1 + 0.2 ≠ 0.3 这类误差，单价设为整数元即可避免；按 24 小时周期计算比按自然日简单，停车时长相同则费用相同，容易测试，也容易向用户解释。

**代价**：不支持"每小时 2.5 元"这样的单价；与部分真实停车场按自然日封顶的做法不同。

**重新评估的条件**：需要支持小数单价时，改用"分"为单位的整数，而不是改用浮点数。

## ADR-006：分配固定车位后车位状态为"占用"

**状态**：已采纳

**背景**：REQ-007 要求"释放后车位变为空闲"，但没有规定分配后的状态。车位状态只有 free、occupied、reserved 三种，其中 reserved 留给 REQ-022 的时间段预约。

**可选方案**：
1. 分配后状态改为 occupied，释放后改回 free。
2. 分配后状态不变，仍为 free，只用 fixed_vehicle_id 是否为空区分是否已分配。

**决定**：方案 1。

**原因**：已分配的车位不应再被分配、预约或删除。方案 1 直接沿用已有规则（occupied 的车位不能删除，只能分配 free 的车位），不需要在每处额外检查 fixed_vehicle_id；状态一眼可见，门卫不会把它当空位。

**代价**：固定车位的车辆不在场时，车位仍显示占用，REQ-018 的利用率把它计为占用，利用率表示"已被占用或已分配"，而不是"此刻场内停了多少车"。

**重新评估的条件**：如果入场登记改为分配车位（见任务卡 A-3 规则 5），需要区分"已分配"和"有车停着"，届时考虑增加状态或单独统计在场车辆。

## ADR-007：角色权限按页面整页隐藏，用白名单

**状态**：已采纳

**背景**：REQ-020 要求门卫"看不到住户管理、车辆管理、车位管理、收费规则、用户管理的修改入口"。这五个页面分属 A、B、C、D 四个人；需求没有提到数据备份页。

**可选方案**：
1. 整页隐藏：门卫的侧边栏里没有这些页面。只改 A 的 `auth.py` 和 `main_window.py`。
2. 页面可看、按钮隐藏：各页面加只读参数，门卫能查看但不能修改。需要 B、C、D 各改自己的页面。

权限表的写法：白名单（列出每个角色能用的功能）或黑名单（只列门卫不能用的功能）。

**决定**：方案 1，白名单；门卫同样不能使用数据备份页。

**原因**：方案 1 不涉及其他成员的文件，可以一次完成并测试；门卫的日常工作是出入登记和查询，不需要查看住户、车位资料。白名单下新增页面默认对门卫关闭，忘记登记只会"看不到"，不会"误开放"。还原备份会覆盖整个数据库，风险高于修改单条资料，所以虽然需求没有列出，也只给管理员。

**代价**：门卫无法查看住户、车辆、车位信息（例如核对某车是否为月租车）；新增页面时必须在 `auth.py` 登记，否则管理员也看不到。

**重新评估的条件**：门卫确实需要查询这些资料时，改为方案 2，由各页面负责人增加只读模式。

## ADR-008：备份还原用 sqlite3 的 backup 接口，还原后退出程序

**状态**：已采纳

**背景**：REQ-023 要求一键备份、可从备份还原。程序运行期间一直持有同一个数据库连接，各页面都通过它读写。

**可选方案**：
1. 用 `shutil.copy2` 直接复制 `parking.db` 文件；还原时关闭连接、覆盖文件、重新打开。
2. 用标准库 `sqlite3.Connection.backup` 在两个连接之间复制数据。

还原后的处理：提示后退出程序，或只提示、让各页面自行刷新。

**决定**：方案 2；还原前自动备份当前数据；还原成功后提示并退出程序。

**原因**：连接开着时直接复制文件，可能拿到写了一半的数据；Windows 下文件被占用时无法覆盖。backup 接口由 SQLite 保证复制出一致的完整数据，还原时直接写进当前连接，不用关闭重开，测试也能用内存库。还原后已打开的页面持有旧数据，用户表也可能变化（当前账号可能已不存在），退出后重新登录最稳妥。还原前自动备份，误还原时还能找回。

**代价**：备份文件只能用 SQLite 打开；还原后要手动重新启动程序；每次还原都会多出一份自动备份，需要手动清理。

**重新评估的条件**：备份文件过多时，增加"只保留最近 N 份"的清理规则。

## ADR-009：出入记录只保存入场操作员

**状态**：已采纳（A 与 D 商定，第二批）

**背景**：`records.operator` 在入场时写入。`GateService.exit` 也接收 `operator` 参数，但没有保存，看不出出场是谁办理的（#44 审查遗留）。

**可选方案**：
1. 不保存出场操作员，记录只保留入场操作员。
2. 给 `ParkingRecord` 和 `records` 表增加 `exit_operator` 字段，出场时写入。

**决定**：方案 1。

**原因**：方案 2 要改 `app/models/` 的已有数据类和建表语句，按项目规则需要全组同意并同步修改测试；第二批的目标是基础功能收尾并打 v0.1，这项改动不影响任何需求的验收。

**代价**：出场操作无法追溯到人。`exit` 的 `operator` 参数暂时保留不用，避免改动已有接口。

**重新评估的条件**：需要按操作员统计或追责出场操作时，改为方案 2。

## ADR-010：入场不分配车位，车位状态由人工维护

**状态**：已采纳（A 与 D 商定，第二批）

**背景**：入场登记时 `records.space_id` 固定为空，车位状态不随车辆进出变化。因此（1）车位页面可以把"占用"手动改为"空闲"，与 `records` 中仍在场的车辆对不上（#44 审查遗留）；（2）REQ-018 的利用率不能反映场内实际停车数（任务卡 A-3 规则 5）。两个问题根源相同，一并决定。

**可选方案**：
1. 入场不分配车位，车位状态由管理员在车位页面维护，保留手动修改。
2. 入场时选一个空闲车位改为占用，出场时释放；车位状态由出入流程自动维护，取消手动修改。

**决定**：方案 1。

**原因**：方案 2 要同时改 D 的 `gate.py` 和入场页面、C 的车位逻辑，并与固定车位（ADR-006）、车位预约（REQ-022）配合，第二批来不及；需求清单也没有要求入场分配车位。

**代价**：利用率表示"已分配或标记为占用的车位 ÷ 车位总数"，不是"此刻场内停了多少车"，实训报告中需说明；车位状态可能与实际停车情况不一致，依赖管理员维护。

**重新评估的条件**：进阶阶段时间充裕，或演示时需要利用率随车辆进出变化时，改为方案 2，届时由 D 与 C 共同出任务卡。

## ADR-011：车位预约只记录时间段，不改变车位状态

**状态**：已采纳（A 决定，任务卡 A-5）

**背景**：REQ-022 只要求"为某车牌预约某个空闲车位的某一时间段；同一车位的预约时间段不能重叠"。车位状态只有一个值（free / occupied / reserved），而预约是带时间段的，可能是明天甚至下周的。

**可选方案**：
1. 预约只是时间段记录，不改变车位状态；状态为 occupied 的车位不能预约，free 和 reserved 都可以。
2. 第一条预约时把车位状态改为 reserved，预约全部取消后改回 free；只能预约 free 或 reserved 的车位。

**决定**：方案 1。车牌只校验格式（REQ-005），不要求已登记。

**原因**：状态不分时间段，方案 2 会让明天的预约导致车位今天就显示"预约"，与实际不符，还要在取消预约时维护状态；方案 1 与 ADR-010"车位状态由人工维护"一致，改动最少。occupied 包括已分配的固定车位（ADR-006），这类车位不应被别人预约。访客和临时车多数没有登记，要求登记会让预约功能基本不可用。

**代价**：预约不会自动反映在车位状态和利用率上；入场登记不检查预约（与 ADR-010 一致，入场不分配车位），预约起提醒和防重叠作用。

**重新评估的条件**：入场流程改为分配车位（ADR-010 方案 2）时，一并考虑入场时检查预约。
